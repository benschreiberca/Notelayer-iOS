# v1.5.0 Crash-on-Launch — Assessment & Remediation Plan

Status: Active
Last Updated: 2026-06-08
Branch: `claude/v1-5-crash-fix-l4JLW`
Rejected build: commit `3a1b481` ("v1.5.0: Navigation simplification, feature graduation, onboarding overhaul, insights deep links")

---

## TL;DR

Apple's automated review reported the v1.5.0 build **crashed on launch**. This document
captures the assessment and a prioritized remediation plan.

Key conclusions:

1. **The single most important missing artifact is the symbolicated crash log** from App
   Store Connect (Resolution Center) / Xcode Organizer → Crashes. It pinpoints the exact
   faulting frame. Everything below is inference from static analysis because the crash
   cannot be reproduced in CI (no macOS/Xcode/Simulator in this environment).
2. The literal launch screen is defensively coded — no high-confidence exception crash was
   found on the `App → RootTabsView → TodosView` path.
3. The app's documented "crash on launch" history is a **watchdog launch hang
   (`0x8BADF00D`)** that was "hardened" in v1.4.5 but **never validated on a physical
   device** (its plan is stuck at 78%). This is the most likely match for the literal
   "crashed on launch" symptom — and is almost certainly the "this was supposed to be
   resolved" the report refers to.
4. There is a **definite, reproducible crash** when opening **Profile & Settings** or
   **Manage Account** (the in-app **account-deletion** screen Apple reviewers are *required*
   to test): `FirebaseBackendService` is consumed via `@EnvironmentObject` but is **never
   injected** into the environment. Pre-existing (introduced in `30e5c55`), not a v1.5.0
   change, but a high-probability reviewer trigger.
5. **The version was never bumped**: `MARKETING_VERSION` is still `1.4.5` and the build
   number (`CURRENT_PROJECT_VERSION`) is still `1`. This is an independent release blocker
   (a build with a previously-used number cannot be resubmitted).

## Findings

### Finding A — `FirebaseBackendService` environment object is never injected (DEFINITE CRASH)

**Severity:** Critical · **Confidence:** High · **Where:** account/settings screens
**Files:**
- `ios-swift/Notelayer/Notelayer/Views/ProfileSettingsView.swift:6`
- `ios-swift/Notelayer/Notelayer/Views/ManageAccountView.swift:6`
- `ios-swift/Notelayer/Notelayer/App/NotelayerApp.swift:334,349-359`

Both views declare:

```swift
@EnvironmentObject private var backendService: FirebaseBackendService
```

`FirebaseBackendService` is created in `NotelayerApp.init()` as a `@StateObject` but is
**never** passed to the view tree with `.environmentObject(backendService)`. A repo-wide
search for `.environmentObject(` returns only `ThemeManager` and `AuthService` injections —
never `FirebaseBackendService`.

When SwiftUI renders a view that requires an `@EnvironmentObject` not present in the
environment, it traps at runtime:

> `Fatal error: No ObservableObject of type FirebaseBackendService found. A View.environmentObject(_:) for FirebaseBackendService may be missing as an ancestor of this view.`

**Why it matters for review:** This screen is reached from the gear menu → "Profile &
Settings" / "Manage Categories" → account management. Apple Guideline **5.1.1(v)** requires
apps that support account creation to offer in-app account **deletion**, and reviewers
specifically navigate there to verify it. Commit `30e5c55` added that deletion flow "for App
Store submission" — and wired in the un-injected dependency at the same time. A reviewer
exercising account deletion would crash immediately.

This is *not* on the literal first-frame launch path, so it may not be the automated
"launch" crash — but it is a guaranteed reviewer-path crash and must be fixed regardless.

**Fix:** Inject the service once at the root in `NotelayerApp.body`:

```swift
RootTabsView()
    .environmentObject(ThemeManager.shared)
    .environmentObject(authService)
    .environmentObject(backendService)   // add this
```

…and propagate it across the `.sheet`/`.fullScreenCover` boundaries that present those views
(sheets do not inherit environment objects automatically), mirroring how `theme` /
`authService` are already re-injected in `RootTabsView`, `TodosView`, `InsightsView`,
`NotesView`.

### Finding B — Watchdog launch hang (`0x8BADF00D`) hardening was never validated on device (MOST LIKELY "LAUNCH" CRASH)

**Severity:** Critical · **Confidence:** Medium · **Where:** launch / scene-create
**References:**
- `docs/App_Launch_Hang_Untappable_And_Watchdog_Crash_Issue_Report.md`
- `docs/App_Launch_Hang_Untappable_And_Watchdog_Crash_Implementation_Plan.md` (progress: **78%**)

The app has a documented history of launch hangs terminated by the iOS watchdog
(`scene-create` budget exceeded, termination code `0x8BADF00D`), caused by main-thread I/O
during startup. The v1.4.5 hardening (deferred APNS registration, deferred migration,
off-main shared-import processing, guarded single-pass Firebase bootstrap, cached
`ThemeBackground` wallpaper decode, off-main analytics/telemetry) addressed the *design*, but
the plan's **Definition of Done is incomplete**:

- PASS 1 (10 cold launches interactive, no freeze) — not done
- PASS 2 (no scene-create/scene-update watchdog violation, release-style) — not done
- PASS 3 (no `0x8BADF00D` in normal launch) — not done
- PASS 4 (main-thread I/O materially reduced on device) — not done

i.e. the fix was shipped on inference and simulator sanity only; **physical-device,
release-style watchdog validation never happened**. Watchdog terminations are routinely
reported by App Review tooling as "crashed on launch."

**v1.5.0 interaction:** v1.5.0 preserves the launch deferral patterns (`LocalStore.load()`
remains defensive; `migrateIfNeeded()` still deferred 0.75s; shared-import still off-main).
It does **not** obviously regress them. But it adds a fresh-install onboarding sheet
(`WelcomeView`) that presents ~0.5s into launch — exactly the window Apple's automated
fresh-install reviewer exercises — so any residual launch-time main-thread pressure now has
new UI work layered on top during the watchdog-sensitive window.

### Finding C — Version / build number not bumped for v1.5.0 (RELEASE BLOCKER)

**Severity:** High · **Confidence:** High
**File:** `ios-swift/Notelayer/Notelayer.xcodeproj/project.pbxproj`

`MARKETING_VERSION = 1.4.5` and `CURRENT_PROJECT_VERSION = 1` across all configs. The
"v1.5.0" archive therefore carries stale version metadata, and **a build number that has
already been used cannot be resubmitted** to App Store Connect. Must be bumped before any
resubmission.

---

### Finding D — Launch path is otherwise defensively coded (no smoking-gun exception)

A full launch-path audit (`NotelayerApp`, `AppDelegate`, `AuthService`,
`FirebaseBackendService`, `LocalStore.load()/init/migrate`, `RootTabsView`, `WelcomeView` +
onboarding subviews, `ThemeManager`, analytics) found:

- `LocalStore.load()` uses `try?` with safe fallbacks for every decode; empty/first-install
  state is handled (`categories = Category.defaultCategories`).
- Firebase configuration is guarded single-pass (`FirebaseBootstrapper`), invoked before any
  `Auth.auth()` use.
- Onboarding env objects (`ThemeManager`, `AuthService`) and the launch screen
  (`TodosView` → needs `theme` + `authService`) **are** injected at the root.
- The few unsafe-looking subscripts (`ThemeManager` `themes[0]`, `accents[0]`) read from
  arrays populated with literals at compile time and cannot be empty at runtime.
- Entitlements are correctly mapped (Debug → `aps-environment=development`, Release →
  `NotelayerRelease.entitlements` `aps-environment=production`); App Group
  `group.com.notelayer.app` present in both, with `?? .standard` fallback in code.

No high-confidence first-frame exception was identified. This *raises* the relative
likelihood that the launch crash is the watchdog hang (Finding B) and/or a
device/OS-specific issue only visible in the crash log.

## Remediation Plan

### Step 0 — Obtain the crash log (blocking for definitive root cause)
- Pull the symbolicated crash report from **App Store Connect → Resolution Center** (attached
  to the rejection) and/or **Xcode → Organizer → Crashes**.
- Identify the faulting thread/frame and exception type:
  - `EXC_CRASH (SIGABRT)` with a Swift fatal-error string → exception (e.g. Finding A).
  - `0x8BADF00D` / `EXC_RESOURCE` / scene-create watchdog → Finding B.

### Step 1 — Fix the definite crash (Finding A)
- Inject `FirebaseBackendService` at the root and across sheet/cover boundaries that present
  `ProfileSettingsView` / `ManageAccountView`.
- Add a lightweight launch-time smoke check (debug assertion or unit/UITest) that constructs
  those views with the full environment.

### Step 2 — Bump version & build (Finding C)
- `MARKETING_VERSION = 1.5.0`, increment `CURRENT_PROJECT_VERSION` (e.g. to `2`), for **all**
  targets including the share extension (must match the app).

### Step 3 — Close out watchdog validation (Finding B)
- Re-run the v1.4.5 launch-hardening Definition of Done (PASS 1–4) on a **physical device**,
  **release configuration**, debugger detached, including a high-data + fresh-install run.
- Confirm the onboarding sheet presentation does not add first-frame main-thread work; defer
  any non-critical work until after the first interactive frame.

### Step 4 — Reviewer-path hardening pass
- Manually walk the exact path a reviewer takes with the supplied credentials:
  launch → sign in → Profile & Settings → **account deletion** → sign out. Fix any crash or
  dead-end encountered. (Account deletion is mandatory per Guideline 5.1.1(v).)

### Step 5 — Resubmit
- Archive release, validate, upload the new build number, and reply in Resolution Center
  noting the crash fix.

---

## Definition of Done
- [ ] Symbolicated crash log reviewed; faulting frame identified and mapped to a finding.
- [ ] `FirebaseBackendService` injected; Profile & Settings + Manage Account open without crash.
- [ ] `MARKETING_VERSION = 1.5.0` and a fresh, never-used build number set on all targets.
- [ ] 10 consecutive cold release launches on device with no freeze/watchdog termination.
- [ ] Reviewer path (sign in → account deletion → sign out) completes without crash.
- [ ] New build uploaded and rejection responded to.

## Notes
- App Review login credentials (provided out-of-band) are used **after** launch, so they are
  unlikely to be the trigger for an on-launch crash — but they are exactly the path that hits
  Finding A (account management), so they remain in scope for Step 4.
- This environment cannot build/run the iOS app (Linux, no Xcode), so device validation
  (Step 3) must be performed on a Mac with a physical device.
